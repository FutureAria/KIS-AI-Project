# 발표 스크립트

## 3분 발표

안녕하세요. 이 프로젝트는 한국 주식 데이터를 기반으로 AI가 모의투자 판단을 보조하는 `KIS AI 트레이더`입니다.

처음 문제의식은 단순했습니다. AI 투자 서비스에서 사용자는 결과 숫자만 보면 “왜 샀는지”, “왜 기다리는지”, “지금 값이 확정 수익인지”를 알기 어렵습니다. 특히 자동매매처럼 위험한 도메인에서는 판단 근거와 운영 안정성이 기능만큼 중요하다고 봤습니다.

그래서 이 프로젝트는 바로 실거래를 하는 구조가 아니라, 모의투자 검증, AI 판단 근거, 리스크 차단, 히스토리 진실성, 운영 감시를 분리해서 설계했습니다.

백엔드 관점에서는 데이터 수집, 시장 국면 판단, 종목 후보 평가, 리스크 게이트, 모의투자 기록, 운영 점검을 나눴습니다. 가격 데이터는 원천과 fallback을 구분하고, 장중 평가와 마감 확정 기록을 분리했습니다. 실거래 전환도 단순 플래그가 아니라 read-only 조회, 수동 승인, 첫 주문 승인처럼 단계별로 잠그는 방식을 택했습니다.

프론트엔드 관점에서는 사용자가 숫자를 오해하지 않게 하는 데 집중했습니다. 요약 화면에서는 현재 모의자산과 AI 결론을 보여주고, AI 판단 화면에서는 왜 대기하는지, 어떤 데이터가 부족한지 표시합니다. 히스토리 화면에서는 주말이나 휴장일에 새 수익이 생긴 것처럼 보이지 않게 직전 거래일 기준과 fallback 이유를 분리해 보여줍니다.

운영 측면에서는 엔진이 “절대 안 꺼진다”고 가정하지 않았습니다. 대신 heartbeat, watchdog, 오라클 재부팅 복구, 알림, 감사 로그 백업, 통합 점검 리포트를 둬서 꺼지거나 데이터가 빠지면 감지하고 기록하도록 정리했습니다.

이 프로젝트를 통해 배운 점은 투자 AI에서는 예측 정확도뿐 아니라 설명 가능성, 데이터 출처, 운영 안전장치, 공개 범위 관리가 중요하다는 것입니다. 공개 저장소에는 실제 운영 코드나 키는 올리지 않고, 회사에서 설계 의도와 문제 해결 과정을 이해할 수 있는 문서 중심으로 정리했습니다.

## 5분 발표

안녕하세요. `KIS AI 트레이더`는 한국 주식 데이터를 기반으로 AI가 모의투자 판단을 보조하고, 사용자가 AI의 판단 근거와 운영 상태를 확인할 수 있게 만든 대시보드 프로젝트입니다.

이 프로젝트에서 해결하고 싶었던 문제는 “AI가 돈을 벌 수 있나” 하나가 아니었습니다. 실제로 사용자가 더 자주 마주치는 문제는 AI가 왜 매수하지 않는지, 데이터가 충분한지, 장이 안 열리는 날의 숫자가 진짜 수익인지, 그리고 서버나 엔진이 멈췄을 때 알 수 있는지였습니다.

그래서 프로젝트의 방향을 자동 주문보다 검증 가능한 모의투자와 설명 가능한 판단 구조에 두었습니다.

첫 번째는 데이터 계층입니다. 가격, 뉴스, 공시, 수급, 해외장 선행 지표, 호가와 체결 품질 같은 데이터를 받아 AI 판단에 사용합니다. 여기서 중요한 점은 단순히 값을 가져오는 게 아니라, 값의 출처와 신선도를 함께 관리한다는 점입니다. 예를 들어 KIS 원천값인지, Yahoo fallback인지, 장중 값인지, 마감 확정 값인지 구분해 화면에서 오해가 생기지 않도록 했습니다.

두 번째는 판단 계층입니다. AI는 단순히 매수/대기만 말하지 않고 시장 국면, 공시 리스크, 데이터 부족, 호가 품질, 보유 비중, 후보 사후 결과를 함께 봅니다. 너무 공격적으로 매수하는 것도 위험하지만, 너무 보수적이라 좋은 후보를 계속 놓치는 것도 문제라고 보고, 안 산 후보의 이후 성과도 기록하는 구조를 잡았습니다.

세 번째는 프론트엔드입니다. 화면은 요약, 모의투자, AI 판단, 종목 정보, 히스토리, 운영 상태로 나눴습니다. 특히 히스토리 화면에서는 누적 손익과 하루 변화를 분리했습니다. 주말이나 휴장일에는 새 손익 기록을 만들지 않고 직전 거래일 기록을 표시하며, 이 값이 fallback이라는 것을 명확히 구분합니다.

네 번째는 운영 안정성입니다. 처음에는 엔진이 계속 켜져 있어야 한다고 생각할 수 있지만, 실제 운영에서는 꺼지지 않는 것보다 꺼졌을 때 감지하고 복구하는 구조가 더 현실적입니다. 그래서 heartbeat로 판단 루프 생존을 확인하고, watchdog과 주기 점검으로 서비스와 데이터 freshness를 확인했습니다.

다섯 번째는 실거래 보호입니다. 이 프로젝트는 실거래를 바로 여는 구조가 아닙니다. 실계좌 read-only 조회, 키 회전, shadow mode 리뷰, 수동 승인, 첫 주문 1회성 마커 같은 단계를 모두 통과해야 합니다. 아직 외부 키나 실제 실계좌 증적이 필요한 항목은 완료로 표시하지 않고 `확인 필요` 또는 `외부 설정 필요`로 남깁니다.

마지막으로 공개 GitHub 전략입니다. 운영 코드, API 키, 서버 경로, 로그, 계좌 정보는 공개하지 않고, README, 아키텍처, API 명세 요약, 트러블슈팅, 면접 설명, 운영 안정화 설계처럼 평가자가 문제 해결 과정을 이해할 수 있는 문서만 공개했습니다.

## 발표 때 강조할 키워드

- 설명 가능한 AI 판단
- 모의투자 우선 검증
- 휴장일/장중/마감 데이터 분리
- 데이터 출처와 fallback 표시
- heartbeat 기반 운영 감시
- 실거래 전환 단계 분리
- 공개 GitHub 보안 범위 관리
